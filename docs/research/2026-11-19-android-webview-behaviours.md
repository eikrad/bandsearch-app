# Android WebView behaviours the mobile UI spec depends on

Research for #316 (map #314). Written 2026-11-19 on the throwaway branch
`research/android-webview`. **Facts and a recommendation only — nothing here is
built.** Every claim names its source; confidence is High (read in source code or
first-party docs), Medium (first-party docs, but the exact Tauri setup was not run),
or UNKNOWN (needs the phone).

## Answers

### 1. System back

**Answer.** Yes, the app can intercept it from JavaScript, with no native code:
`onBackButtonPress(handler)` from `@tauri-apps/api/app`, available since
`@tauri-apps/api` 2.9.0. Registering a handler replaces the default completely;
the handler gets `{ canGoBack }` and must decide everything itself. The permission
it needs (`core:app:allow-register-listener`) is in `core:app:default`, so
`core:default` already covers it. To actually leave the app from inside the
handler, call `exit()` (`@tauri-apps/api/app`, since 2.12.0). That needs
`core:app:allow-exit`, which is **not** in the default set and must be added to the
capability. On Android `exit` calls `activity.finishAffinity()`.

**The default is not "Tauri closes the app".** With no listener registered,
Tauri's `AppPlugin` calls `webView.goBack()` whenever `webView.canGoBack()` is
true, and finishes the activity only when there is no history left.
`createHashRouter.ts:39-43` navigates by assigning `location.hash`, which adds a
history entry each time. So an unhandled back press walks back through the hash
history: from Chat after logging in it would return to `#/login` or
`#/connecting`, and the app only closes once that history runs out. Either way
the spec's conclusion stands (back has to be handled), but the reason it gives is
wrong.

**Sources.**
- `node_modules/@tauri-apps/api/app.d.ts:243-285` (API docs, `@since 2.9.0`,
  "Registering a handler takes over the default behavior");
  `app.js:279-280` (`addPluginListener('app', 'back-button', …)`).
- `tauri-2.12.5/mobile/android/src/main/java/app/tauri/AppPlugin.kt:28-46`
  (default: `goBack()` if `canGoBack()`, else `activity.onBackPressed()`;
  with a listener: `trigger("back-button", {canGoBack})`), `:51-55` (`exit` →
  `finishAffinity()`).
- `tauri-2.12.5/mobile/android-codegen/TauriActivity.kt:15`
  (`handleBackNavigation = false`, so wry's own back handler is disabled and
  `AppPlugin` is the only one).
- `tauri-2.12.5/permissions/app/autogenerated/reference.md:1-14` (default set
  includes register/remove-listener, not `exit`).

**Confidence.** High.

**Device test.** Register a handler that logs and does nothing: back and the
back gesture both reach it, and the app stays open. Then call `exit(0)` from Chat:
the app closes. Also check how it looks on Android 14+ with predictive back.
Because Tauri's callback is always enabled, expect no "peek home" animation
(Medium; not verified).

**Design note for #156.** Leaving the app with `exit()` destroys the activity, so
the next launch is a cold start (API wake-up, auth check). Android's usual
"background the task" (`moveTaskToBack(true)`) is not available from JS. It
would need a few lines of Kotlin. That is a product choice, not a blocker.

### 2. Edge-to-edge insets

**Answer.** The spec says edge-to-edge is "required, since Android 15 enforces
edge-to-edge". That understates it. The generated `MainActivity` calls
`enableEdgeToEdge()`, so the app is edge-to-edge on **every** Android version,
including Android 10 to 14, not only on 15+. Content draws under the status bar
**and** the navigation bar. The spec only mentions the bottom inset, but the
header and the fixed `UpdateBanner` (`ui/UpdateBanner.ts:36`) will sit under the
status bar too.

Whether `env(safe-area-inset-*)` works depends on the **WebView** version, not
the Android version:

| WebView | `systemBars()` + `displayCutout()` → `env(safe-area-inset-*)` |
|---|---|
| < M136 | not forwarded (system bars report 0) |
| M136 – M143 | forwarded for **fullscreen** WebViews only |
| ≥ M144 | forwarded for all WebViews |

Tauri/wry add nothing on top. wry 0.57's Android Kotlin code has no inset
handling at all (no `setOnApplyWindowInsetsListener`, no CSS variables). So on
a current WebView the WebView itself provides the values, and on an old one
nothing does. Current stable Android WebView is M158/M159 (Chromium Dash,
2026-11), so a Play-updated Android 10 phone is well past M144.

**Cheapest reliable approach.** Use CSS: `padding-bottom: env(safe-area-inset-bottom, 0px)`
on the tab bar, and `env(safe-area-inset-top)` on headers and the update banner.
Add `viewport-fit=cover` to the viewport meta in `public/index.html` (harmless
on desktop; whether WebView needs it is UNKNOWN, see below). No native code for
v1. A native fallback that forwards insets as CSS variables (about 15 lines of
Kotlin in `MainActivity`, the pattern Capacitor ships) is only worth adding if
testers turn up with a WebView older than M144.

**Sources.**
- Android Developers, "Understand window insets in WebView" —
  <https://developer.android.com/develop/ui/views/layout/webapps/understand-window-insets>
  (the M136/M139/M144 table; "WebView forwards these dimensions to web content
  through CSS safe-area-inset-* variables").
- Android Developers, Android 15 behaviour changes, "Edge-to-edge enforcement" —
  <https://developer.android.com/about/versions/15/behavior-changes-15#edge-to-edge>
  (the system bars become transparent and the top and bottom offsets are removed
  once the app targets 35+).
- Android Developers, "Display content edge-to-edge" —
  <https://developer.android.com/develop/ui/views/layout/edge-to-edge>
  ("To enable edge-to-edge on previous Android versions, manually call
  enableEdgeToEdge").
- Tauri template: `MainActivity.kt` at `tauri-cli-v2.12.6`; tauri-apps/tauri#12182
  (closed by #13780).
- `wry-0.57.0/src/android/kotlin/*.kt` — grep for `inset` finds nothing.
- Chromium Dash `fetch_releases?channel=Stable&platform=Android` →
  `159.0.8154.18` (fetched 2026-11-19).

**Confidence.** High for the edge-to-edge facts and the version table. Medium for
"a Tauri WebView counts as fullscreen on M136–143": it fills an edge-to-edge
activity, but this was not tested.

**UNKNOWN, needs the phone.** (a) Whether `env(safe-area-inset-bottom)` is
non-zero **without** `viewport-fit=cover` in the WebView, and with it. Render a
debug strip showing `getComputedStyle` of a `padding: env(...)` element under
both metas. (b) The values in gesture-navigation mode compared with 3-button mode.

### 3. Soft keyboard

**Answer.** From WebView M139, the keyboard (IME inset) **resizes the visual
viewport only**, for all WebViews. The layout viewport, `100vh` and
`window.innerHeight` do not change. Consequences:

- `position: fixed; bottom: 0` (the planned tab bar) is anchored to the layout
  viewport, so it ends up **behind** the keyboard. That roughly matches "hidden
  while the keyboard is open", but the hiding should be explicit (for example a
  `keyboard-open` class), not a side effect.
- The composer at the bottom of `.bandsearch-chat-shell { min-height: 100vh }`
  (`public/styles.css:124-128`) does **not** move up by itself. The page only
  becomes scrollable so the focused input can be scrolled into view. "Composer
  sits directly above the keyboard" therefore needs JavaScript.

**Detection, cheapest reliable way.** Listen to `window.visualViewport`'s
`resize` event (Chrome 62+). Treat the keyboard as open when
`window.innerHeight - visualViewport.height` is larger than a threshold of about
150 px. Then set a CSS variable such as `--keyboard-inset` and a
`keyboard-open` class on the root, or size the chat shell to
`visualViewport.height`. Android's own page warns: do not `blur()` in response to
these resize events, or the keyboard closes again in a loop.

**Not recommended:** the VirtualKeyboard API
(`navigator.virtualKeyboard.overlaysContent` + `env(keyboard-inset-height)`,
Chrome 94+, WebView listed as mirroring Chrome in MDN BCD). It is a second,
less-documented path in WebView, and how it interacts with M139's IME resizing is
UNKNOWN. `windowSoftInputMode="adjustResize"` is no fix either. Under
edge-to-edge the window is not resized for the IME (the app must handle IME
insets), and WebView handles them itself from M139 on.

**Older WebViews (< M139).** The visual viewport does not resize at all. Under
edge-to-edge the keyboard simply covers the bottom of the page. Only Android 10
devices without Play-updated WebView are affected. Fixing it needs native code
(an IME-insets listener that pads the WebView). Not worth it for v1.

**Sources.**
- "Understand window insets in WebView" (above): "Starting in M139, the input
  method editor (IME) directly resizes the visual viewport", "Previously, the
  visual viewport remained fixed, often hiding input fields behind the keyboard",
  plus the `blur()` loop warning.
- MDN browser-compat-data (`api/VisualViewport.json`, `api/VirtualKeyboard.json`,
  `css/types/env.json`, read 2026-11-19): VisualViewport `resize` Chrome 62;
  VirtualKeyboard Chrome 94; `webview_android: "mirror"`.
- Tauri manifest template: no `windowSoftInputMode`.

**Confidence.** High for the M139 mechanism (first-party). Medium that the
`innerHeight - visualViewport.height` heuristic gives clean numbers inside Tauri's
WebView.

**UNKNOWN, needs the phone.** Log `innerHeight`, `visualViewport.height` and
`visualViewport.offsetTop` on focus and blur of the chat input, in both gesture
and 3-button navigation. Confirm that (a) `innerHeight` stays constant, (b) the
difference matches the keyboard height, and (c) the event also fires when the
keyboard is dismissed with the system back gesture. That last case matters
because back also reaches `onBackButtonPress`. **Check whether the IME's back
press is consumed by the IME or forwarded to the handler.** Normally Android
closes the IME first and does not dispatch to `OnBackPressedCallback`, but this
was not verified in Tauri.

### 4. External links

**Answer.** They work on Android through the plugin that is already used, with no
change needed. `openExternalLink.ts` calls `@tauri-apps/plugin-opener`'s
`openUrl`. On Android this runs `OpenerPlugin.open`, which fires
`Intent.ACTION_VIEW` with `FLAG_ACTIVITY_NEW_TASK`. That opens the default
browser, or the Spotify, Bandcamp or SoundCloud app if it claims the URL as an
App Link (`platformLinks.ts` builds plain `https://` search URLs). The existing
capability `opener:allow-default-urls` allows `http(s)`, `mailto` and `tel`.
`startActivity` with `ACTION_VIEW` needs no `<queries>` manifest entry. That
entry is only needed to *query* other packages.

Two side facts:
- The opener plugin also injects a click listener (`open_js_links_on_click`,
  default on) that routes `<a target="_blank">` clicks to `open_url`. The comment
  at `openExternalLink.ts:12` ("does nothing in the Tauri webview") describes the
  WebView without the plugin.
- The `window.open` fallback (`openExternalLink.ts:7-9`) is effectively dead on
  Android. wry's `RustWebChromeClient` does not implement `onCreateWindow`, and
  WebView's default `supportMultipleWindows` is false. If the opener ever
  rejected (for example with no browser installed), the fallback would not open a
  browser. Its exact behaviour (nothing at all, or navigating the app's own
  WebView away) is UNKNOWN.

**Sources.** `tauri-plugin-opener-2.7.0/android/src/main/java/OpenerPlugin.kt`
(`ACTION_VIEW` / Custom Tabs for `with: "inAppBrowser"`);
`…/permissions/allow-default-urls.toml`; `…/src/lib.rs:205-259` + `src/init-iife.js`;
`wry-0.57.0/src/android/kotlin/RustWebChromeClient.kt` (override list, no
`onCreateWindow`).

**Confidence.** High.

**Device test.** Tap Bandcamp, SoundCloud and Spotify on a card, once with the
Spotify app installed and once without.

### 5. Storage and the auth token

**Answer.** `authTokenStore.ts:1-21` keeps the bearer token in
`localStorage["bandsearch_auth_token"]`. The chat session id
(`chatSessionStore.ts`) and the update-banner dismissal
(`startDesktopBrowserApp.ts:78-95`) live there too. On Android:

- **Persists across restarts:** yes. wry sets `domStorageEnabled = true`, and
  WebView keeps DOM storage under the app's private data directory (`app_webview`).
- **Persists across updates:** yes, as long as the package id (`app.bandsearch`)
  and signing key stay the same *and* the origin does not change. The page origin
  is `http://tauri.localhost` (`useHttpsScheme` defaults to false). Tauri's
  config docs warn that flipping `useHttpsScheme` between releases "will change
  the IndexedDB, cookies and localstorage location and your app will not be able
  to access the old data". **Do not touch `app.windows[].useHttpsScheme` after the
  first release**, or every tester is silently logged out.
- **Lost on:** uninstall, and "Clear storage" in Android's app info.
- **Not on desktop: Auto Backup.** The template manifest does not set
  `android:allowBackup`, so it defaults to `true`. Auto Backup covers files under
  `getDir(...)` (which includes `app_webview`), so **the bearer token can be
  copied into the user's Google Drive backup and restored onto a new device**.
  Android's own docs advise against backing up credentials this way. Cheapest
  fix: `android:allowBackup="false"` in the generated manifest (one attribute),
  or `dataExtractionRules` excluding `app_webview`. This is a closed-beta app with
  an API-side session, and re-login is cheap, so turning backup off costs
  nothing.
- **Is a stronger store needed?** `localStorage` sits in the app's sandbox
  (other apps cannot read it on a non-rooted phone). The plan's "no storage
  switch" covers the database, not the token, and nothing in the spec requires
  Keystore-backed storage. Recommendation: keep `localStorage` for v1, disable
  backup, and document it.

**CORS (for completeness).** The WebView origin `http://tauri.localhost` calls
`https://bandsearch-api.onrender.com`. The API's CORS origin is
`runtimeConfig.corsOrigin || "*"` (`services/api/src/app.ts:91-93`,
`services/api/src/config/env.ts:109`), and `render.yaml` sets no `CORS_ORIGIN`,
so this works today. Anyone who sets `CORS_ORIGIN` later must include
`http://tauri.localhost`. Note also that this is http-to-https, which is not mixed
content, so it is fine.

**Sources.** `wry-0.57.0/src/android/kotlin/RustWebView.kt:21-24`;
`tauri-utils-2.10.4/src/config.rs:2213-2223` (`use_https_scheme` warning);
`tauri-2.12.5/src/manager/mod.rs:790-798` (`http://tauri.localhost/` vs
`https://…`); Android Developers, "Back up user data with Auto Backup" —
<https://developer.android.com/identity/data/autobackup> (defaults, included
directories, `allowBackup` default `true`, credentials tip).

**Confidence.** High for persistence and origin. Medium that `app_webview` is in
the backup set: it falls under `getDir()`, which the docs list, but no actual
backup was inspected.

**Device test.** Log in, force-stop, relaunch (still logged in). Install a
newer-versioned APK signed with the same key (still logged in).
`adb shell bmgr backupnow app.bandsearch` with backup on, then check whether
the restore brings the token back.

### 6. WebView floor (minSdk 29)

**Answer.**
- **How it updates:** from Android 10 on, WebView is its own app
  (`com.google.android.webview`) that updates independently of the OS. On a
  Google-services phone that happens automatically through the Play Store, so it
  is evergreen. Chrome 139+ requires Android 10, so Android 10 is still a
  supported platform today. Current stable is M158/M159.
- **What Android 10 ships with:** AOSP `android-10.0.0_r1` bundles WebView
  **74.0.3729.186**. A phone that never receives WebView updates (no Play
  services, or updates disabled) can be on M74 or another old OEM version.
- **What the frontend needs:** the production bundle is built by esbuild with
  **no `target`** (`apps/desktop/scripts/build.ts:5-10`), so modern syntax passes
  through untouched. Parsing a fresh minified build with acorn fails at ES2019 on
  `l?.forEach(...)` and at ES2020/2021 on public class fields, and passes at
  ES2022. Optional chaining and `??` need **Chrome 80**, and public class fields
  need Chrome 72. **On an un-updated M74 WebView the bundle does not parse: blank
  screen, no error UI.** Runtime APIs found in the bundle (`globalThis`,
  `Promise.allSettled`, `flatMap`, `queueMicrotask`) are all Chrome ≤ 76. No
  `structuredClone`, `.at()`, `Object.hasOwn`, `replaceAll`, `findLast` or
  `toSorted` appear.
- **CSS:** the views use `100vh` (`styles.css:127`, `ConnectingView.ts:42`,
  `LoginView.ts:70`, `SettingsView.ts:726`, etc.), `gap` on flex and grid
  (flex `gap` needs Chrome 84), and `position: fixed`. **No `dvh`, `svh`, `env()`,
  `:has()` or container queries are used today.** `dvh`/`svh`/`lvh` would need
  Chrome 108. Since the IME no longer resizes the layout viewport (M139), `100vh`
  is stable and correct for the shell, and `dvh` is not needed.
- **Practical floor for the features in this spec:** M144 for safe-area insets
  on all WebViews, and M139 for keyboard resizing. Any Play-updated phone meets
  both.

**Recommendation.** Do not add a polyfill or transpile target for v1. Either
(a) leave it as is and put "Android System WebView must be up to date" in the
tester instructions, or (b) cheaper still for diagnosis, add a tiny inline
`<script>` in `index.html` that checks `navigator.userAgent` for
`Chrome/(\d+)` < 80 and writes a plain-HTML "Please update Android System
WebView" message. That turns a blank screen into a readable message. Setting
`target: "chrome80"` in esbuild is also cheap, but it only moves the problem
(insets and keyboard still need M139/M144).

**Sources.** AOSP `platform/external/chromium-webview` log at
`android-10.0.0_r1` — "WebView AOSP Integration Request - 74.0.3729.186";
Chrome for Developers, WebView overview — <https://developer.chrome.com/docs/webview>
("WebView has an APK so it can be updated separately from Android"; Android 10:
"two separate apps"); Chromium Dash stable releases (above); MDN BCD
(`css/types/length.json` viewport units Chrome 108; `css/types/env.json`
`env()` 69); acorn parse of the bundle (script in the research session, not
committed).

**Confidence.** High for the syntax floor and the AOSP version. Medium for
"Play-updated phones are on M158+": that is true of the stable channel, but OEM
rollout lag was not measured.

**Device test.** Open `chrome://inspect` against the phone, or log
`navigator.userAgent` on launch, and record the WebView version of the test phone.

### 7. `matchMedia("(max-width: 767px)")`

**Answer.** It works and stays a sound trigger, with one consequence the spec
should state.
- Media-query px are CSS px (density-independent), so phones in portrait are
  360–430 px wide → `mobile`. Android WebView defaults to
  `useWideViewPort = false`, so the layout width equals the WebView width in CSS
  px. The `width=device-width` meta in `public/index.html:5` agrees, so there is
  no 980 px desktop-emulation surprise.
- The keyboard changes only the visual viewport (M139+), so it **does not** flip
  the breakpoint.
- **Rotation does.** A phone in landscape is about 780–930 CSS px wide, so the
  desktop layout appears (no tab bar, header buttons). Foldables unfolded and
  tablets (≥ 768) also get desktop. `startDesktopBrowserApp.ts:35-48` already
  re-renders on `change`, and the activity is not recreated on rotation
  (`configChanges` includes `orientation|screenSize`), so the switch happens live
  and keeps state. Either accept this and say so in the spec, or lock the
  activity to portrait (`android:screenOrientation="portrait"` in the generated
  manifest). That is a product decision.
- The `minWidth: 800` / `minHeight: 600` in `tauri.conf.json` describe a desktop
  window. Whether Tauri applies them on Android is UNKNOWN (expected: ignored).
  Confirm on the phone that the page is not 800 px wide.

**Sources.** `startDesktopBrowserApp.ts:19-48`; Android `WebSettings.setUseWideViewPort`
(default false — Android API reference); MDN BCD; the manifest template above.

**Confidence.** High for portrait and keyboard. Medium for landscape widths
(they vary by device).

## Surprises that affect the plan

1. **Exports are dead on Android.** "Export my data" (Art. 15/20, which the
   privacy policy points users to) and "Export" of saved artists both use
   `Blob` + `URL.createObjectURL` + `<a download>.click()`
   (`ui/mountDesktopReactApp.ts:409-415`, `:512-518`). Android WebView only
   downloads through a host-supplied `DownloadListener`, and wry 0.57's Android
   code registers none (grep `download` in `wry-0.57.0/src/android/` finds
   nothing). A `blob:` URL also cannot be handed to `DownloadManager`. Expect
   the click to do nothing (UNKNOWN until tested, but high likelihood). Cheapest
   workaround: on Android, hand the JSON to the share sheet (`navigator.share`
   with a `File`, which Android WebView does not implement either, so verify) or
   save through `tauri-plugin-fs` / a dialog plugin. This needs its own ticket on
   the map. Import (`<input type=file>`) should work, because wry implements
   `onShowFileChooser`. Verify it on the device.
2. **Auth token goes into Google Drive backups by default** (see §5). One manifest
   attribute fixes it. Add it to the Android CI/release ticket.
3. **`useHttpsScheme` must be frozen** from the first APK on, or every update logs
   everyone out (§5).
4. **Blank screen on stale WebViews.** The bundle needs Chrome ≥ 80 and has no
   error UI below that (§6).
5. **`targetSdk = 37` from the template.** Edge-to-edge cannot be opted out of
   (it cannot be disabled when targeting Android 16+, per a Tauri maintainer in
   tauri-apps/tauri#12182), and predictive back is the default. Both are already
   covered by the answers above. No action, but do not plan around an opt-out.
6. **Outside this ticket, but found while reading:** the Rust crate has only
   `src/main.rs` with `fn main()` (`src-tauri/src/main.rs:617`). Tauri mobile
   needs a `lib.rs` with `#[cfg_attr(mobile, tauri::mobile_entry_point)] pub fn run()`
   and a `[lib] crate-type` including `staticlib`/`cdylib` (Tauri docs, "Upgrade
   from Tauri 1.0 › Preparing for Mobile" and "Project structure"). Also,
   `tauri_plugin_updater` is registered unconditionally (`main.rs:620`) and the
   capability lists `updater:default` (`capabilities/default.json`). The plan says
   it must be `#[cfg(desktop)]`. Both are first steps of the build ticket, not
   UI-spec issues.

## Review amendments (Opus, independent, 2026-11-19) — verdict: APPROVE WITH CHANGES

An adversarial reviewer re-checked against the pinned crate sources (`tauri` 2.12.7, `wry` 0.57.0, `tauri-utils` 2.10.4) and Android/Chromium docs. Facts held; four *recommendations* rested on wrong assumptions or skipped a safer option. These amendments **replace** the earlier recommendations where they conflict.

| # | Amendment | Status |
|---|---|---|
| 1 | **Back handling: prefer a history model over `onBackButtonPress` + `exit()`.** With no listener and no WebView history, Tauri falls through to the platform default, and since **Android 12 a root launcher activity is moved to the background, not finished** (Android 12 behaviour changes, all apps). So `exit()` means a cold start on every back-out of Chat, needs a new `core:app:allow-exit` permission, and behaves unlike every other app. Preferred design — make the hash history *be* the spec's back order and register **no handler**: auth transitions (connecting → login → chat) use `location.replace`; Chat is the root; opening Saved/Settings from Chat pushes one entry; switching between Saved and Settings replaces that entry; edge screens and open sheets push an entry and a sheet closes on `popstate`. WebView `goBack()` then reproduces the order, and on the Chat root it reaches the system default. Testable in a plain narrow browser window, logic stays in `createHashRouter.ts`. Fallback: handler + ~10 lines of Kotlin `moveTaskToBack(true)`. **Spec text to correct:** default is "walks hash history, then backgrounds (Android 12+) or finishes (10/11)", not "closes the app". | Adopted → mobile-layout decision |
| 2 | **Backup: `allowBackup="false"` alone does not protect the token.** On API 31+ it "doesn't disable device-to-device transfers" (developer.android.com/identity/data/autobackup); template `targetSdk` is 37. Add `android:dataExtractionRules` excluding `app_webview` (or everything) in both `<cloud-backup>` and `<device-transfer>`, `android:fullBackupContent` for 10/11, keep `allowBackup="false"`. Device test (`bmgr`, D2D if possible) in the release ticket. | Adopted |
| 3 | **Threat model: it is not "an API-side session".** `services/api/src/auth/authService.ts:9,62,75` issues a stateless JWT, `expiresIn: "30d"`, **no revocation**; `clearAuthToken` only deletes the local copy. A leaked or backed-up token stays valid ≤ 30 days with no kill switch. `localStorage` is acceptable for v1 (sandboxed; release builds have WebView debugging off, `wry-0.57.0/src/android/main_pipe.rs:256`) **only if** backup is excluded and no debuggable APK reaches testers. Server-side revocation (token version or `jti` denylist) is the real fix. | Adopted → security/posture decision |
| 4 | **Exports: drop the share-sheet option; use one narrow Rust command.** `navigator.share` is not available in Android WebView. `plugin-fs` from JS works (via `content://` URIs from `plugin-dialog`'s `save()`) but hands the webview broad `fs:` write permission. Recommended: a custom `save_export(filename, json)` command that calls the dialog plugin's Rust API and writes via `FsExt::open` — no fs permission in the webview, and desktop gets the same "Save as" path (one implementation, no platform branch). This is the Art. 15/20 control the privacy policy points to, so **severity: blocks the beta**, not a "surprise". | Adopted → new ticket |
| 5 | **External links: make the fallback fail visibly.** wry sets `javaScriptCanOpenWindowsAutomatically = true` (`RustWebView.kt:25`) and implements no `onCreateWindow`, so `window.open` likely navigates the app's own WebView away. Guard the fallback with `isTauri()` and show an error inside Tauri; optionally an `on_navigation` hook blocking origins other than `tauri.localhost`. | Adopted → mobile-layout decision (as a robustness rule) |
| 6 | **WebView floor: boot watchdog + explicit esbuild `target`**, not only UA sniffing. An inline ES5 script in `index.html` catches `SyntaxError` via `window.onerror` and shows "update Android System WebView" if the bundle has not set a boot flag within a few seconds. Set an explicit esbuild `target` (none today) so a future syntax change fails the build instead of silently raising the floor. | Adopted → mobile-layout decision |
| 7 | **Keyboard heuristic: harden it.** `innerHeight − visualViewport.height > 150` also fires on pinch-zoom; require `visualViewport.scale === 1` (or disable zoom) and use `innerHeight − vv.height − vv.offsetTop`. Do **not** hide the tab bar on focus alone — dismissing the IME with back usually leaves the input focused. | Adopted |
| 8 | **Capabilities.** `capabilities/default.json` uses `desktop-schema` and includes `updater:default`; mobile needs its own capability with `"platforms": ["android"]`. | Adopted (build issue) |
| 9 | **Lock portrait for v1** (`screenOrientation="portrait"`): at ~400 px height plus keyboard the desktop layout is untested and near-unusable. On Android 16+ with targetSdk ≥ 36, locks are ignored on large screens (sw ≥ 600 dp); phones unaffected. | Adopted → mobile-layout decision |
| 10 | Defence in depth: a CSP with `connect-src` limited to the API host. No `innerHTML`/`dangerouslySetInnerHTML` sinks were found in `apps/desktop/src`, so this is hardening, not a fix. | Deferred (low) → security/posture decision |

**Also missed by the research:** back pressed before the async listener registers takes the default `goBack()` path (harmless under amendment 1); import file filter — wry turns `accept=".json,application/json"` into an `EXTRA_MIME_TYPES` filter (`RustWebChromeClient.kt:411-416`), so a JSON file labelled `application/octet-stream` may be greyed out → add to the device test.

**Corrections to confidence levels:** that `window.innerHeight` stays constant with the IME on M139+ has no first-party statement (Medium, not High); `viewport-fit=cover`'s effect on `env(safe-area-inset-*)` stays UNKNOWN.

**Not verified by the reviewer:** whether a Tauri WebView counts as "fullscreen" on M136–143; whether IME dismissal by back reaches `onBackButtonPress`; what `window.open` actually does in Tauri on Android (source reading says in-app navigation, not run); `navigator.share` absence (from memory); the Chrome-80 floor of the bundle (acorn parse not re-run).
