# Android (Phase 11)

Outcome of a design session on 2026-08-30. Records what was decided, what is
forced by the platform, and what the roadmap got wrong. Not yet implemented.

The roadmap's Android entry was three lines: `tauri android init`, voice input
via the Web Speech API, and a "responsive layout review". Two of those three
turned out to rest on false premises, and the third is much larger than it
sounds.

## Why Tauri, still

The PWA was considered as an alternative and rejected — but only *after* the
distribution and voice decisions below, which require an APK and a native
plugin respectively. A PWA can do neither. Tauri is the consistent answer here,
not the leftover one: desktop already ships on it, with one frontend, one Rust
backend and one release workflow.

## Forced by the platform (not decisions)

1. **No Node sidecar on Android.** Tauri's shell plugin on mobile is
   [restricted to opening URLs](https://v2.tauri.app/plugin/shell/) — no child
   processes, no executing binaries. Android also forbids executing binaries
   from app-writable storage. `better-sqlite3` is out for the same reason.
   → Android is remote-API-only. `reconcile_sidecar()` already has that branch;
   Android simply always takes it.

2. **`tauri-plugin-updater` does not support Android.** The official setup
   registers it under `#[cfg(desktop)]`. The update banner from Phase 10 will
   never appear on Android. Our `let Ok(updater) = … else` already fails soft.

3. **The Web Speech API does not work in Android WebView.** The roadmap claimed
   it "works natively in Chromium-based Android webviews — no native plugin
   needed". It does not: the object exists but no callbacks fire
   ([Chromium 487255](https://issues.chromium.org/issues/40417848), open since
   2015). It works in Chrome *on* Android, which is not what Tauri embeds.

## Decisions

### API endpoint (#159) — compiled-in default, overridable

The Android build ships the production URL as its default; the existing
Settings field from Phase 9.4 stays, so anyone can point the app at their own
instance. Rationale: the project is Apache-2.0 and self-hosting should work.

Implementation note: the default must be **platform-conditional**. Today
`should_run_local_sidecar()` (`apps/desktop/src-tauri/src/main.rs`) returns
true for an empty endpoint, so an un-configured Android build would try to
start a sidecar that cannot exist. On Android, Rust returns the production URL
as the default and never takes the sidecar branch; the frontend already reads
the endpoint from `gemini_config_status.apiEndpointUrl` and follows
automatically.

**The production URL is `https://bandsearch-api.onrender.com`** — confirmed
2026-09-28 by hitting both candidates directly: `bandsearch-api.onrender.com`
returns the API's own JSON 404 (`{"error":{"code":"not_found","message":"route
not found: /"}}`, i.e. a live Express process with no route at `/`, consistent
with `render.yaml`'s `name: bandsearch-api`), while `bandsearch.onrender.com`
returns Render's own "no such service" page.

**Found in the course of confirming this: the `-api` was missing everywhere
else it was hardcoded.** `SettingsView.ts`'s placeholder text, every test
fixture standing in for the production endpoint and the example in
`docs/ROADMAP.md`'s Phase 9.4 entry all used `https://bandsearch.onrender.com`
— the non-existent one. Harmless while it was only a placeholder or a test
double, but a real bug the moment anyone copied it as an endpoint, and the
wrong string to compile into the Android default. Fixed in #224 (issue #223).

Compiling in the provider's own hostname rather than a domain of our own is
deliberate for now — no real users yet, and hosting is revisited before
launch anyway; see ADR 0003.

### Voice (#157) — native microphone button with a settings toggle

Binding spec: `docs/design/UI_GUIDELINES.md`'s Voice Input section. The
[mockup](https://claude.ai/artifact/GanWpZoaWJxPyn4nCFpNKQ) (Chat and Settings
screens) is private and illustrative only.

A Kotlin Tauri plugin wrapping Android's `SpeechRecognizer`, a microphone
button in the composer, and a Settings switch that hides it and never requests
`RECORD_AUDIO`.

Noted for context: Android's soft keyboard (Gboard, Samsung) already offers
voice typing into the chat `<input>` with zero code. That covers dictation, but
it cannot be toggled by the app — the keyboard belongs to the user — which is
why the toggle requirement implies the native button.

Behaviour decided in the 2026-09-28 grilling session:

- **Engine: the phone's own `SpeechRecognizer`, not a bundled model.** This
  does *not* guarantee on-device recognition: `SpeechRecognizer` uses whatever
  recognition service the phone has — Google's on most phones, whose audio may
  be processed on Google's servers; a FOSS service if the user installed one;
  often none at all on phones without Google services. A bundled offline
  engine ([sherpa-onnx](https://k2-fsa.github.io/sherpa/onnx/index.html),
  Apache-2.0) was considered — audio would never leave the phone and it would
  work everywhere — and rejected for now on implementation effort and
  +40–150 MB of model size. Note that either way only the *audio* is at stake:
  the recognised text is the query and goes wherever a typed query goes — the
  pipeline's LLM provider (Gemini today; selectable per #179) and Brave.
- **Off by default, opt-in with a notice.** *(Revised the same day — the
  first version had the button visible by default. Changed once it was clear
  the audio may go to a third party.)* The Settings switch starts off;
  turning it on first shows a notice ("Depending on your phone, your voice may
  be sent to a third party to be processed — on most phones, that's Google")
  with Cancel / Turn on. `RECORD_AUDIO` is requested on the first mic tap
  after that, never at launch or at the switch.
- **No recognition service → no control.** If
  `SpeechRecognizer.isRecognitionAvailable()` is false, neither the button nor
  the Settings switch renders (the "no control without an action" rule in
  `UI_GUIDELINES.md`). Implementation note: from Android 11 the manifest needs
  a `<queries>` entry for the `android.speech.RecognitionService` intent, or
  this check returns false even when a service exists.
- **Disclosure when it ships.** `privacyPolicyText.ts` and
  `docs/architecture/2026-08-30-data-flow-and-eu-residency.md` gain the
  voice-audio flow as part of #157 — not before, or they would describe a
  feature that doesn't exist.
- **Permission denied.** An inline hint appears above the composer
  ("Microphone access denied") with an "Open Android settings" button that
  opens Android's app-info page for Bandsearch, plus a × to dismiss. Not "our
  Settings": ours only has the on/off switch, the permission lives in
  Android's, and after "Don't ask again" the app cannot ask a second time.
  The button itself stays visible but visibly inactive (muted colour, no
  listening animation on tap). Tapping the (inactive) button again while still
  denied re-shows the hint if it was dismissed.
- **Transcript handling.** Recognised text fills the composer input; the user
  reviews and sends it manually. No auto-submit — `SpeechRecognizer` misreads
  band names and slang often enough that sending straight to the API would
  regularly fire a query nobody typed.

### Distribution (#158) — own F-Droid repository

APKs built and signed in CI, index published (GitHub Pages is enough), testers
add the repo once via QR. The F-Droid client then handles update notifications
and installs.

This is what closes the updater gap: **Android needs no update code of its
own.** Official F-Droid inclusion was considered and rejected for now — it
requires reproducible builds, which
[F-Droid documents as hard for Rust/NDK](https://f-droid.org/docs/Reproducible_Builds/),
plus a metadata recipe, review, and a `NonFreeNet` anti-feature label because of
Gemini and Brave.

Release mechanics decided in the 2026-09-28 grilling session, working from the
existing release-please pipeline (`docs/releasing.md`):

- **Same pipeline, same tag as desktop.** No separate Android release cycle.
  `release.yml` builds the signed APK as another artifact of the same
  `vX.Y.Z` release that already builds Linux/Windows/macOS, and publishes it
  into the F-Droid repo's index alongside them. One version number for the
  whole project, one process to maintain — see `docs/releasing.md`'s "How a
  release happens" section for the Android step now folded in.
- **`versionCode` derived from semver — Tauri's own default.** Tauri already
  computes `major*1000000 + minor*1000 + patch` from `tauri.conf.json`'s
  `version` (so `0.4.0` → `4000`); leave `bundle.android.versionCode` unset and
  let it. Never hand-set, consistent with "Nobody edits version numbers by
  hand" in `docs/releasing.md`. *Corrected 2026-09-28:* the first version of
  this bullet specified a custom `major*10000 + minor*100 + patch`, which
  collides at patch 100 (`0.4.100` = `0.5.0`) — and pre-1.0,
  `bump-patch-for-minor-pre-major` makes every `feat`/`fix` a patch bump, so
  that limit is the one most likely to be hit.
- **Test builds never reach the F-Droid repo.** A `v0.4.1-test` tag yields the
  same `versionCode` as the real `v0.4.1`; a tester who installed the test APK
  would never be offered the real release.
- **F-Droid index metadata reuses README.md and CHANGELOG.md.** The short
  description comes from the README's opening line; each release's F-Droid
  changelog entry is the same release's `CHANGELOG.md` section release-please
  already generates. No separate fastlane-style metadata files to keep in
  sync by hand.

### Mobile layout (#156) — bottom tab bar, single-scroll Settings, bottom action bar

Binding spec: `docs/design/UI_GUIDELINES.md`'s Mobile Navigation section,
which also covers the system back gesture, the keyboard hiding the tab bar,
edge-to-edge insets and the viewport trigger. This section is the rationale.
The [mockup](https://claude.ai/artifact/GanWpZoaWJxPyn4nCFpNKQ) is private and
illustrative only; the text is the spec.

- **Navigation — bottom tab bar.** Replaces the two small header buttons
  ("Settings" / "Saved" in `ChatAppView.ts`, `padding: 5px 12px` — well under
  the locked 44px touch target, a defect this replacement also fixes). Three
  tabs: Chat, Saved Artists, Settings. Scoped to those three views only —
  Login, Register, ResetPassword, Welcome, Connecting and PrivacyPolicy do not
  get it.
- **Edge screens get a back arrow, not the tab bar.** Register and
  ResetPassword go back to Login; PrivacyPolicy goes back to Settings. 44px
  header button, `←`. Welcome and Connecting need no new navigation — they
  already have their own locked flows (Skip/Continue, and the single "Try
  again" retry button from the Connecting State spec).
- **SettingsView stays single-scroll.** No accordion/collapsible sections —
  the existing structure just gets the 16px mobile padding and 44px targets
  from the already-locked responsiveness policy.
- **SavedArtistsView selection bar — at the bottom.** Selection in this view
  exists only to pick style references; its bar (`SelectionBar`) has a single
  action, "Use as style reference". On mobile it moves to directly above the
  tab bar, the most thumb-reachable spot. *Corrected 2026-09-28:* the first
  version of this section (and of the mockup) described bulk Delete / Group /
  Export actions — those were assumed during the grilling session rather than
  read from the code, and do not exist. Delete is per card, Export and "Group
  by genre" are page-level.
- **No local/Turso storage switch on Android.** SettingsView's desktop
  migration UI ("Connected to Turso… Switch back to local SQLite") doesn't
  apply on Android — there is no local SQLite path to switch from or to (see
  "Forced by the platform" above: no `better-sqlite3` on Android, ever).
  Android's Settings "Connection" section shows only the API endpoint field.

### Offline behaviour — error message only

No cache, no dedicated offline screen. A missing connection surfaces through
the existing paths — `ConnectingView` at launch, the chat error banner
mid-session — with Android-appropriate copy (see Work items below).
Consistent with "Android is remote-API-only" above: Phase 5.5's local-first
work for the desktop is not ported, not even partially.

### Hosting — Render Free

Chosen over Fly.io on cost grounds, accepting the 30–60s cold-start wake as a
known trade-off rather than paying ~$0.15/month for Fly.io's ~300ms–2s
scale-to-zero. The 61 MB RSS measurement (see Sequencing below) means either
tier's smallest instance has headroom; the choice was cold-start-vs-cost, not
capacity. EU residency was not a differentiator — `render.yaml` already pins
compute to Frankfurt, and Fly.io has a Frankfurt region too; see
`docs/architecture/2026-08-30-data-flow-and-eu-residency.md`. Recorded as
[ADR 0003](../../adr/0003-android-hosting-render-over-fly.md).

### Android CI — minSdkVersion 29, single production keystore, pinned NDK

- **`minSdkVersion` 29** (Android 10, 2019), raised above the Tauri default of
  24 to keep the test matrix small: Android 10+ covers most devices in use,
  and three fewer old versions (7–9) need testing and support. No
  app-specific API dependency forces it, at the cost of excluding Android 7–9.
- **Signing** — one production keystore, base64-encoded in GitHub Actions
  secrets (`ANDROID_KEYSTORE_BASE64`, `ANDROID_KEY_ALIAS`,
  `ANDROID_KEY_PASSWORD`, `ANDROID_STORE_PASSWORD`). No upload/signing-key
  split: that separation exists in Play App Signing because Google re-signs
  the APK, which doesn't apply to a self-hosted F-Droid repository.
- **Two aliases in that keystore** — one signs the APK, one signs the F-Droid
  repo index (`fdroid update` needs its own key; the first version of this
  section missed it).
- **Offline backup is mandatory.** GitHub secrets can't be read back. If the
  keystore exists only there and the local copy is lost, installed apps can
  never be updated again — only uninstalled and reinstalled. Keep an
  encrypted copy offline (e.g. password manager plus a USB stick), with the
  passwords stored separately from the keystore file.
- **An Android build failure blocks the whole release**, desktop included —
  deliberately: every platform ships the same version, or none does. See
  `docs/releasing.md`.
- **NDK** — an exact version pinned in the release workflow rather than left
  to Tauri's auto-detect/install. Keeps CI builds reproducible and is a step
  toward the reproducible-builds bar noted above for eventual official F-Droid
  inclusion (still rejected "for now", unchanged by this decision).

Offline behaviour needs no new *mechanism*, but it does need new *copy* —
fold it into #156. Two paths already exist:

- **Offline at launch** → the first status check fails → `ConnectingView`'s
  `failed` state ("Could not reach the server", pointing at Settings).
- **Offline mid-session** → `fetch` throws a `TypeError` →
  `apiErrorMessages.ts` maps it to "Could not reach the Bandsearch API. If the
  app just started, wait until the API is ready, then try again."

Both texts were written for the desktop sidecar (a local process that is
still starting, or a wrong endpoint). On a phone, the likelier cause is no
network, and neither text says so. *Corrected 2026-09-28:* this paragraph
previously claimed the existing banner already covered Android.

Hosting needs no work item — it's an operational choice for Phase 9.5's
deployment, not new code.
